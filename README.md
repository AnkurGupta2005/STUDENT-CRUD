# Students Database CRUD API

A Python backend for managing student records, built with **FastAPI** and **SQLite**.
It supports Create, Read, Update and Delete, input validation, and an **optional** local-AI
endpoint that answers questions about the data using **Ollama**.

## Features

- Full CRUD on `/students` with filtering and pagination
- Data stored in a SQLite file (`students.db`), so it survives restarts
- Validation: required fields, email/phone format, date checks, unique email
- Clear errors: `404` for missing records, `409` for duplicate emails, `422` for invalid input
- Interactive API docs at `/docs` (Swagger UI)
- 45 automated tests (`pytest`)
- Optional bonus: `POST /ai/ask` answers natural-language questions with a local Ollama model

## Prerequisites

- Python 3.10 or newer
- (Optional, for the AI bonus) [Ollama](https://ollama.com) installed

## Installation

```bash
git clone <your-repo-url>
cd students-crud

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

## Run the server

```bash
uvicorn app.main:app --reload
```

The database file and table are created automatically on first start.
Open **http://127.0.0.1:8000/docs** to try every endpoint in the browser.

Optional: load some dummy data first (all made up):

```bash
python seed.py
```

## Student fields

| Field | Required | Notes |
|---|---|---|
| `id` | auto | Unique integer, generated by the database |
| `name` | yes | 1 to 100 characters |
| `date_of_birth` | yes | `YYYY-MM-DD`, between 1900-01-01 and today |
| `email` | one of email/phone | Valid format, unique, stored in lower case |
| `phone` | one of email/phone | At least 7 digits; `+`, spaces, `-`, `()` allowed |
| `course` | no | |
| `address` | no | |
| `enrollment_date` | no | `YYYY-MM-DD`, must be after date of birth |

## API endpoints

| Method | Endpoint | Purpose | Success |
|---|---|---|---|
| POST | `/students` | Create a student | 201 |
| GET | `/students` | List / filter students | 200 |
| GET | `/students/{student_id}` | View one student | 200 |
| PUT | `/students/{student_id}` | Replace all details | 200 |
| PATCH | `/students/{student_id}` | Update only the fields you send | 200 |
| DELETE | `/students/{student_id}` | Delete a student | 204 |
| POST | `/ai/ask` | (Optional) Ask a question about the data | 200 |

**Filters on `GET /students`** (all optional, combinable):
`name` (substring), `course` (substring), `email` (exact), `born_after` and `born_before`
(`YYYY-MM-DD`, strictly after / before), `skip` and `limit` (pagination, limit max 500).

## Testing the API with curl

```bash
# Create
curl -X POST http://127.0.0.1:8000/students \
  -H "Content-Type: application/json" \
  -d '{"name":"Aarav Sharma","date_of_birth":"2004-05-17","email":"aarav@example.com","course":"Computer Science"}'

# List, and filter
curl http://127.0.0.1:8000/students
curl "http://127.0.0.1:8000/students?course=computer&born_after=2003-01-01"

# View one
curl http://127.0.0.1:8000/students/1

# Update some fields
curl -X PATCH http://127.0.0.1:8000/students/1 \
  -H "Content-Type: application/json" -d '{"course":"Data Science"}'

# Replace everything
curl -X PUT http://127.0.0.1:8000/students/1 \
  -H "Content-Type: application/json" \
  -d '{"name":"Aarav Sharma","date_of_birth":"2004-05-17","email":"aarav@example.com","phone":"+91 90000 00001"}'

# Delete
curl -X DELETE http://127.0.0.1:8000/students/1

# Missing record -> 404
curl http://127.0.0.1:8000/students/999
```

## Run the automated tests

```bash
pytest
```

Tests use a temporary database, so your real `students.db` is never touched.
The AI tests mock Ollama, so no model is needed to run them.

## Optional: ask questions with Ollama

1. Install Ollama and download a small model:
   ```bash
   ollama pull llama3.2:1b
   ollama serve        # skip if Ollama is already running in the background
   ```
2. Start the API and add some data (`python seed.py`).
3. Ask a question:
   ```bash
   curl -X POST http://127.0.0.1:8000/ai/ask \
     -H "Content-Type: application/json" \
     -d '{"question":"How many students are there?"}'

   curl -X POST http://127.0.0.1:8000/ai/ask \
     -H "Content-Type: application/json" \
     -d '{"question":"List students born after 2005."}'
   ```

The response contains the `answer`, plus the records that were given to the model
(`records_used`) and the `filters_applied`, so every answer can be checked against the data.

**Settings** (environment variables, all optional): `OLLAMA_URL` (default
`http://localhost:11434`), `OLLAMA_MODEL` (default `llama3.2:1b`), `STUDENTS_DB`
(default `students.db`). If Ollama is not running, `/ai/ask` returns `503` with a
helpful message and the rest of the API is unaffected.

### How the AI stays safe and accurate

- **The model never runs SQL and never touches the database.** The backend decides what to fetch.
- It recognises a few fixed patterns in the question (birth year such as "born after 2005",
  a course name that exists in the data, a student's name) and runs normal parameterised queries.
- The matching records and **exact counts calculated in Python** go into the prompt, and the model
  is told to answer only from them. Small models are unreliable at counting, so it is not asked to.
- Even a malicious question can only change the wording of the answer, since the model has no tools.
- Only dummy data is used in the seed script. Do not commit real student information.

## How records are created, updated and deleted (architecture)

1. A request hits a route in `routers/students.py`.
2. FastAPI/Pydantic validates the JSON body (`schemas.py`). Bad input stops here with a `422`.
3. The route calls a function in `crud.py`, which runs a parameterised SQL statement on SQLite
   (no string-built SQL, so no SQL injection).
4. **Create** inserts a row and returns it with its new `id`. **Update** loads the current row,
   merges the changes (PATCH) or replaces it (PUT), re-validates the final record, then saves it.
   **Delete** removes the row. A missing `id` gives `404`, a duplicate email gives `409`.
5. Each request uses its own short-lived database connection, which is always closed afterwards.
